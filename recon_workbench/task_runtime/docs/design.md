# 任务运行管理设计

状态：PR1、PR2、PR3 已实现持久化队列、受控并行、CPU/GPU 资源账本、按任务取消、POSIX 进程组清理、阶段恢复和离线备份恢复。真实算法工具恢复按环境单独验收。基线：`127c485`，本地单工作区服务。
各 PR 合并时在本文相应章节补充实现位置、已支持平台、偏差和实测证据。

## 1. 当前行为与目标

| 当前代码 | 当前行为 | 目标 |
| --- | --- | --- |
| `server.py::Jobs.start` | 单个 `self.process`，已有计算就拒绝 | PR1 先持久化入队，后台派发 |
| `workspace.py::create_task/recover` | 保存历史；未结束任务标记中断 | PR1 执行尝试和安全重启；PR3 恢复 |
| `pipeline.py::build_plan/main` | 顺序执行路线，拒绝已有输出目录 | PR3 新尝试目录、经过校验的阶段复用 |
| `reconstruct.py::Pipeline.run` | 每层新 session，正常 SIGINT 逐级传播 | PR1 统一可追踪的进程所有权与清理 |
| `web/common.js/workbench.js/projects.js` | 全局单任务和 running 假设 | PR1 队列与按任务操作；PR2 多运行任务 |

选择 Python 后台调度器 + SQLite 事务 + 本地文件系统。
备选为外部消息队列和独立 worker，但当前单机需求不需要部署额外服务；不引入 Redis/RabbitMQ。
现有直接 CLI 不经队列执行，其 CPU/GPU 占用不在服务账本内；在文档和资源页面明确此边界。

## 2. 模块职责和接入

- `server.py`：请求校验、Token/Host、响应和已有工作区权限边界；`Jobs` 仅适配 `task_runtime.service.RuntimeJobs`，不存放调度循环。
- `workspace.py`：保留项目、图片集、模型与历史接口；初始化时调用本包增量迁移。
- `task_runtime/repository.py`：队列、attempt、条件状态更新；claim 与终态在显式事务内完成。
- `snapshots.py`：提交前固定输入并以哈希清单发布 staging；不得把后来变化的原目录交给算法。
- `scheduler.py`：唤醒、查队列、claim、启动握手、失败收敛；PR1 一个执行槽，PR2 资源预算。
- `processes.py/worker.py`：包装进程组、身份登记、取消和进程树退出确认。
- `resources.py`：PR2 资源需求和分配；不负责 HTTP 或算法质量。
- `recovery.py/validators.py`：PR3 阶段计划、来源验证和恢复执行，不修改算法实现。
- `backup.py`：PR3 离线备份 CLI；使用工作区锁，不通过任意 HTTP 路径恢复数据库。
- `pipeline.py` 和算法适配层：保留命令组装和执行，接入进程控制与阶段事件。

新代码以本包为主；公共文件仅增加必要调用、查询和页面适配。
用户权限由其他组员实现，HTTP 查询/取消/恢复仍必须经 task → project 归属检查，不能做第二套鉴权。

## 3. 不变量

1. 一个逻辑任务一个稳定 task_id；每次执行一个 attempt_id，同一 task 最多一个活动 attempt。
2. 队列先有可验证输入再可执行；不得提交后读取后来改变的筛选名单。
3. claim 与分配原子提交；启动命令来自持久化的已校验参数，不执行客户端任意命令。
4. 状态由后台写入，HTTP 轮询只读；旧 attempt、旧 generation 不能覆盖新尝试或终态。
5. `completed` 要求计算成功、所需产物验证、摘要发布和模型登记完成。
6. `cancelling` 只表示请求已接受；确认全部计算退出前不能释放资源或报告取消完成。
7. 不能确定进程是否残留时阻止可能冲突的派发；不得只凭旧 PID 结束进程。
8. 重试、恢复和备份不覆盖输入原件、旧 attempt 或成功模型，不把预览抽样当原始产物。

## 4. PR1：持久化队列

### 状态和顺序

```text
preparing → queued → starting → running → completed
    │          │          │         ├→ failed
    │          └→ cancelled         └→ cancelling → cancelled
    └→ failed
starting/running/cancelling --异常中断→ interrupted
failed/interrupted --PR3 恢复→ queued（新 attempt）
```

`preparing` 用于已登记任务但快照还未完成的窗口，不允许派发。
使用数据库 `queue_seq` 保证 FIFO，排序为 queue_seq 升序；首版不提供优先级、无限自动重试或暂停训练。
收到同参数新请求默认创建不同任务；提供幂等键时复用提交记录，见 api.md。

### 提交、输入和派发

1. 校验项目、输入类型、路线参数和质量确认；记录原始参数和标准化请求摘要。
2. 事务中占用幂等键并登记 preparing；已占用且仍准备中的同键请求返回原任务状态。
3. 原始照片复制已确认文件到 staging，验证哈希、写 selection/quality 清单，原子发布任务输入目录。
4. SfM/Brush 复用输入同样需要固定其照片、模型及依赖清单；采用独立副本或可靠不可变版本，不仅保存目录字符串。
5. 事务创建队列项并变 queued 后才允许派发。复制失败记 failed；崩溃遗留 staging 在下次启动核对并标明，不静默消费。
6. 调度器在 `BEGIN IMMEDIATE` 中 claim 并创建 attempt；PR1 在同一事务检查没有其他活动尝试。
7. 事务外启动受控执行器。启动失败保存错误和终态，下一任务仍可调度。
8. 后台消费退出事件，验证/发布结果并登记模型，持久化终态，唤醒调度器。

condition/event 唤醒用于新提交、退出、取消；定期扫描作为丢失唤醒补偿，不做忙循环。
本项目不承诺外部命令“严格恰好一次”：子进程启动和 SQLite 之间无法原子提交。
使用 attempt 目录、启动握手和中断核查避免在未知窗口自动重复执行。

### 进程所有权与取消

在 Linux/WSL 本地 Linux 子进程、macOS 上，服务调度的每次执行建立一个可辨识会话/进程组。
执行器/包装进程先登记 attempt、PID/PGID、启动标识并等待允许执行握手，持久化完成后才启动计算。
受控非交互算法子进程继承所有者进程组，不逐层无条件 `start_new_session=True`。
PTY/Brush 如需独立 session，必须显式登记附属组并保持监督器存活；不能以“所有进程一定同组”为假设。
禁止 shell=True；只操作本 attempt 的已验证身份，严禁按程序名全局 pkill。

取消事务先记录 cancel_requested_at，条件转换为 cancelling；队列/准备中任务只阻止发布和派发。
运行任务由后台执行 SIGINT → 等待10秒 → SIGTERM → 等待5秒 → SIGKILL；超时可配置，HTTP 不阻塞等待。
确认已登记进程组及子孙进程退出，回收句柄/PTY/监控线程，再写 cancelled。
父进程先退出不能视为整棵树已结束；取消监控异常需重扫而非马上派发下一任务。
终态先提交则后来的取消不修改结果；取消先成功提交则旧完成回调不能覆盖，终态为 cancelled。

支持平台必须实际测试；若某工具绕开进程组或跨 Windows 边界，需专门后端（例如 Job Object）后才能启用。
本期先支持经验证的本地 Linux/macOS 进程树；WSL 启动 Windows Brush 等未支持组合在预检拒绝。

### 重启和关闭

维持现有 workbench.lock 单实例锁。正常关闭先停止派发，保留 queued，再取消/清理活动执行，等待监控持久化。
SIGKILL、断电或监控异常后，下次启动按 attempt 身份、启动握手和产物核对真实状态。
已完成但数据库未提交的任务经校验登记；未完成标 interrupted。
残留进程经身份核验后清理；身份不确定标记 reconciliation_required 并停止派发，显示原因及人工核查步骤。
heartbeat 只表示最近观察，超时不证明进程已死；不以过期 heartbeat 自动释放执行槽。
PR1 不自动重跑 interrupted；PR3 提供显式恢复入口。

## 5. PR2：资源与并行

配置示例（示例值需根据机器调整，不是自动探测承诺）：

```json
{
  "schema_version": 1,
  "cpu_slots": 8,
  "max_running_tasks": 3,
  "gpu_devices": [{"id": "gpu0", "backend": "cuda", "selector": "GPU-示例UUID"}]
}
```

配置放在 `data/task_runtime/resources.json`，读取时严格校验；没有配置默认单执行槽、GPU 禁用。Fast3R 始终要求 `cuda`，未配置或身份探测失败时拒绝启动；当前 Brush 没有经过核验的设备选择适配器，因此服务队列拒绝 3DGS GPU 任务。其它路线可通过 `method_backends` 显式声明已验证的 CUDA 后端。
重启应用配置，首版不做运行中缩减额度。探测提供提示，配置给出允许预算，两者含义不能混淆。
CPU 额度大于0且不超过总预算；GPU 路线也声明 CPU 预算，默认与实际线程参数保持一致。
所有额度按整条任务预留；允许 SfM 期间预留 GPU 的低效率，阶段级重新分配留待后续。

事务中读取未释放分配 → 查最老可运行项 → 写资源行 → claim。一个 GPU 同时只分给一个 attempt。
无法满足当前余量的任务继续 queued，动态计算 waiting_reason；超出总预算、未配置兼容 GPU 的请求在提交时拒绝。
允许跳过等待 GPU 的任务执行可满足的 CPU 任务；此规则可能使大任务等待，不宣称严格 FIFO 或公平性保证。

CPU 额度下传 `--threads`、适用库变量和 PyTorch 线程配置；参数需写入执行记录。
这是服务内的预算与工具线程约束，不是 OS CPU 硬配额；不实现 cgroup，不限制系统外任务。
GPU 采用经 `nvidia-smi` 核验的稳定 UUID，不接受数字设备序号；CUDA_VISIBLE_DEVICES 仅选卡，子进程中可见设备可能重新编号。
Brush 按后端单独验证；无法可靠选卡的后端只允许经验证的单卡配置，不宣称多 GPU 支持。
NVML/nvidia-smi 查询失败返回 unknown，不把未知当零或空闲；监控数值不是显存保证。
GPU 外部占用可作为预检/等待原因，但不能阻止外部程序之后抢占；OOM 记录为失败，不无限重试。

分配按 attempt_id 释放一次。Popen 失败可直接释放；进程已启动则必须确认进程树退出。`GET /api/resources` 展示持久化预算、占用、可用和 GPU 观察字段；`POST /api/queue-resume` 只能在残留核查通过后解除派发暂停。
终态但清理仍未知的尝试继续占用；重启通过持久化账本和进程核查重建使用量，不能初始化为0。

## 6. PR3：阶段恢复

恢复单位按实际依赖选择，首版清单：

| 单元 | 复用条件 | 重做边界 |
| --- | --- | --- |
| SfM | 相机/图像/点模型及状态/摘要在完整哈希清单中，来源指纹一致 | 特征、匹配、mapper 作为一个单元重新执行 |
| MVS 去畸变/转换 | 视图、内参、路径及 scene.mvs 可供后续工具读取 | 从最早无效单元开始 |
| MVS dense | 原生 dense.mvs、PLY 和视图依赖有效 | 失败则重做 dense 及其后继 |
| MVS mesh | 原生 mesh.mvs、非空有效顶点/面 | 可保留 dense，重做 mesh/textured |
| MVS textured | OBJ/MTL/纹理引用都存在且有效 | 重做纹理单元 |
| Brush 准备 | dataset.json、照片、相机/点二进制、尺寸/引用有效 | 准备失败则重做；训练可从新数据开始 |
| Brush 训练 | 最后请求步数导出完整，评估与模型摘要一致 | 重新训练，不以 export PLY 充当优化器 checkpoint |
| Fast3R | 已保存输入/配置、全局点云可解析、统计对应 | 整段推理重跑，不拼接不同尝试局部坐标系 |

存在/非空不足以判定成功；结合哈希、格式、依赖、工具版本和配置指纹。
没有历史 manifest 的任务不自动信任；尽可能验证并建来源记录，不能验证则重做相应单元或返回明确原因。
模型内部文件用流式哈希/解析，避免加载整份大型模型。

失败/中断任务可显式 resume；取消任务、成功任务首版拒绝 resume，重新实验应创建新任务。
只读预检给出复用/重做/阻塞列表及 plan_fingerprint；正式恢复再次核对，变化则返回409。
输入内容变化拒绝复用原任务，要求新任务；前置产物损坏可在输入完整时从最早无效节点重做。
工具版本不兼容不静默复用，预检说明原因；未完成阶段仍可从起点重做，真实算法依赖缺失会由原工具预检报错。

每次恢复创建 `attempts/<attempt_id>/`，沿用固定输入和参数；复用文件带 source_attempt_id、路径、哈希。
拷贝到新工作目录并验证，原生 MVS 的内部路径/工作区依赖一起处理，不能只复制一个 PLY。
复制受磁盘可用空间和写入错误约束；第一版不以可写硬链接复用，防止修改历史产物。
原目录已存在的检查保持生效，通过新目录和显式阶段执行入口完成恢复，不删除保护逻辑。

旧目录的 config/status/summary 不覆盖。`current_attempt_id` 指向当前执行，`tasks.output` 仅在成功时切换到新 attempt；状态查询读取当前尝试，历史尝试独立可查。
先验证产物并原子发布摘要，再事务登记模型和终态；两者之间故障由重启核对幂等补齐。
模型保留 attempt 来源，evaluate/records 解析最新已发布结果，失败恢复不覆盖旧成功结果或混算耗时。

## 7. PR3：离线备份与恢复

选择离线完整备份，避免在线复制变化中的大模型造成 DB/文件快照不一致。
备选在线快照需要协调所有文件写入和算法产物提交，本期不实现。
备份 CLI 必须与服务使用同一文件锁：服务在运行即拒绝；离线工具还须核查无残留计算或外部写入。
DB backup API 只保证数据库一致性，不能代替算法文件静止检查。

归档包括 data/outputs 中数据表引用的受管资产与恢复依赖，不局限 data/uploads；登记在这两个目录之外的照片明确拒绝备份，需用户自行整理后再执行。
输入/模型缺失或位于不支持的工作区外部依赖时明确失败；不能悄悄生成不可恢复的“完整备份”。
包含 `data/` 受管数据、`outputs/` 任务/attempt/日志/报告；排除锁、套接字、PID运行文件、staging、工具和环境。
清单采用格式版本、schema版本、文件路径/大小/SHA-256、原工作区根、工具版本；摘要和 manifest 也要结构校验。
归档在 staging 写入、关闭、校验后原子发布到工作区外目标。哈希检测损坏，不是来源真实性认证。

恢复仅接受不存在的新根目录：先校验和解压到同级 staging，禁止绝对路径、..、链接、特殊文件、重复条目、超限展开。
以配置的最大展开字节数/文件数及磁盘余量为界限；SQLite integrity_check 和 foreign_key_check、清单/资产关联均需通过。
只重写定义好的资产路径字段/JSON键，不盲目替换任意字符串；未知必要绝对路径导致阻塞并列出。
原始 command/日志作为审计保留，不直接执行；恢复执行命令由标准化参数重新生成。
旧 PID/PGID/owner 清空、活动 attempt 标 interrupted、旧分配作为历史释放；旧主机不由恢复端接管或杀进程。
queued 任务保留 ID 与序号，但改为 interrupted，原 command 仅作审计；新环境需逐项预检恢复来重建命令。写入 `dispatch_paused` 标记，首次启动核对环境，再显式解除暂停。
验证成功才重命名发布新根目录；失败清理自己创建的 staging，不改原目录，不覆盖已存在目标。

工具和模型权重不随备份分发，恢复到新机器后需配置；“可查看历史”和“可以继续重建”分别验收。
修改前不自动做原地恢复，因此没有危险的数据库在线替换；降级通过旧备份和旧版本另建工作区。

## 8. 失败窗口与补偿

| 窗口 | 可能留下什么 | 收敛行为 |
| --- | --- | --- |
| 快照发布前崩溃 | preparing/staging | 不派发，核对后失败/清理自身临时文件 |
| claim 后未启动 | starting/attempt、PR2分配 | 验证无执行后标中断并释放；不盲目执行 |
| 启动后 PID 未落盘 | 包装执行器未获许可 | 不启动算法；握手身份核对，未知阻止派发 |
| 父进程退出子进程仍活 | 尝试状态和残留进程 | 清理确认前继续占用执行槽/资源 |
| 产物有但摘要没有 | 孤立阶段文件 | 验证后续写或明确重做，不从文件存在推断成功 |
| 摘要有但模型未登记 | 文件与SQLite不一致 | 根据 attempt 和manifest 幂等登记 |
| 取消/完成交叉 | 迟到回调 | 事务条件转换，先提交的终态/取消决定结果 |
| 备份/恢复写到一半 | staging/临时归档 | 不发布正式备份/目标，源保持不变 |

测试对应 [testing.md](testing.md)。实现及自动化证据见 testing.md；真实算法与硬件验收仍未执行。
