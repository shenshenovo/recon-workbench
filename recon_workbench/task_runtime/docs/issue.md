# [任务运行管理] 分三个 PR 实现持久化队列、CPU/GPU 调度、失败阶段与备份恢复

状态：PR1 已在当前分支实现并完成本地代码测试；PR2/PR3 待后续分支实现。目录：`recon_workbench/task_runtime/`。
本文件是 GitHub 总 issue 的仓库副本；issue 地址创建后记录在 [pr-plan.md](pr-plan.md)。

## 问题与目标

基线版本的 `server.py::Jobs` 只保存一个内存中的运行进程，第二个任务被拒绝，没有等待队列。
基线 `workspace.py::recover()` 只识别原有结果或将未结束任务标为 `interrupted`，不会继续执行。
`pipeline.py` 与算法模块拒绝已有输出目录，不能直接复用原命令实现恢复。
上层和底层执行器均使用新进程会话，取消信号依赖逐级传播，强杀父进程可能遗留计算。

交付后，网页任务能排队并跨服务重启保存；依据 CPU/GPU 额度运行；取消后确认进程退出再释放资源；
失败任务可校验产物后恢复；工作区可生成一致性备份并在新目录恢复。

## 范围和边界

包含：本地单机、单工作区服务、Python + SQLite + 文件系统、受控子进程、必要的网页状态适配。
现有 `project_id/image_set_id/task_id`、质量筛选和不可变输入快照必须继续有效。
现有 HTTP Token/Host/路径校验继续生效；任务所属项目不得因调度或恢复改变。

不包含：账号权限、模型下载、增量 SfM、图片重复算法、远程 GPU、分布式 worker、Redis/RabbitMQ、
GPU 显存硬切分、GPU 利用率配额、3DGS 优化器 checkpoint 续训、任意进程接管。
直接运行原有 CLI 继续独立执行，不纳入服务资源账本；资源上限仅约束本服务调度的任务。
Windows 原生进程树及 WSL 启动 Windows Brush 不作未经验证的清理承诺；不支持的执行方式须启动前拒绝并解释。

备份第一版为离线完整工作区备份，恢复到不存在的新目录；不实现运行中模型的热备份、原地覆盖或跨版本降级。
所有新能力按对应 PR 启用；规划文档不得表述为已实现。

## PR1：持久化任务队列与取消清理

建议标题：`feat(runtime): 新增持久化单 worker 队列与按任务取消`。

- [ ] 新增版本化增量迁移与运行记录；旧任务 ID、模型和历史记录不丢失。
- [ ] 提交时完成参数校验、质量筛选校验与输入快照，再提交可调度的 `queued` 任务。
- [ ] FIFO 排序采用数据库递增序号；事务 claim，重复调度不能启动同一次执行两次。
- [ ] 支持可选提交幂等键；同键同参数返回原任务，同键不同参数返回冲突。
- [ ] 第一版最多运行一个任务；第二、第三个任务入队，不再因已有计算而拒绝。
- [ ] 排队任务重启后仍存在并保持顺序；旧运行尝试先核查，不能只凭 PID 重启或误杀。
- [ ] `queued → cancelled` 无子进程；运行中取消先变 `cancelling`，经信号升级确认进程树退出后变 `cancelled`。
- [ ] 处理启动失败、终态与取消竞态、强制结束上层进程；无法确认清理时保持占用/阻止派发。
- [ ] 后台保存最终状态，不依赖网页轮询；停止服务不丢排队任务。
- [ ] 适配工作台、项目记录、全局入口，支持 `queued/cancelling`、按 task_id 轮询和取消。
- [ ] 更新 `api.md`、`database.md`、`design.md`、`testing.md`、`docs/COLLABORATION.md` 和使用说明。

测试与验收：

- [ ] A 运行时提交 B/C，返回稳定 ID、空 PID 和队列位置；A 完成后 B/C 依次自动启动。
- [ ] 重启队列，B/C 的 ID、输入哈希、顺序不变；不可确认的残留任务使派发进入明确的阻塞状态。
- [ ] 两个并发 claim、重复 HTTP 请求、同一任务重复取消不产生重复执行或终态倒退。
- [ ] 用真实 Python 子/孙进程测试正常退出、忽略 SIGINT/SIGTERM、父进程异常退出，证明清理而非只测 mock 调用。
- [ ] 新库、旧库升级、重复迁移、迁移中断回滚及已有根目录测试通过。
- [ ] 浏览器刷新/切页不会取消任务，队列任务可取消，历史日志仍可读。

## PR2：CPU/GPU 资源控制

建议标题：`feat(runtime): 按 CPU 额度与独占 GPU 调度并行任务`。依赖 PR1。

- [ ] 支持受校验的 `cpu_slots/max_running_tasks/gpu_devices` 配置与任务需求记录。
- [ ] CPU 按额度累加；GPU 按整卡独占；GPU 任务也要分配 CPU；整条任务预留资源。
- [ ] 在同一事务中检查额度、记录分配和 claim；并行启动不能超卖 CPU/GPU。
- [ ] 不满足当前余量的任务继续等待并显示原因；请求超过总预算或 GPU 缺失时提交失败。
- [ ] 最老可运行任务优先，可跳过暂时无法满足的任务；不承诺严格 FIFO 或无饥饿。
- [ ] 实际线程参数下传 COLMAP/OpenMVS，适用时设置数学库/PyTorch 线程参数；记录真实执行参数。
- [ ] Fast3R 使用经过验证的 CUDA 设备选择；Brush 单独验证后端，不能机械套用 CUDA 环境变量。
- [ ] GPU 监控能力缺失显示 unknown；GPU 路线无可靠设备确认时拒绝启动，CPU 路线仍可用。
- [ ] 取消/失败后确认进程树退出才释放分配，按 attempt_id 幂等释放；恢复不盲目清空账本。
- [ ] 新增资源查询和界面等待提示，维持按 task_id 查询/取消，不以“当前全局任务”误操作其他任务。
- [ ] 更新三个核心文档、测试矩阵、公共协作及资源部署说明。

测试与验收：

- [ ] CPU=8 时两个各需4的任务并行，第三个等待；GPU=1 时两个 GPU 任务串行。
- [ ] CPU 与 GPU 任务在总额度内可并行；多 GPU 假设备测试不会重复分配同一卡。
- [ ] 取消清理期间新 GPU 作业不能抢占；启动失败、异常监控、重复释放不会泄漏或虚增额度。
- [ ] 超额、无卡、非法配置、设备探测失败、残留进程和数据库异常有可观测结果。
- [ ] 有硬件的机器记录一次真实 CPU+GPU 并行和 GPU 串行；提交工具版本、设备、线程参数、日志、资源时间线。
- [ ] 没有硬件时标记真实 GPU 验收未完成，不以模拟测试宣称实测通过。

## PR3：失败阶段恢复、备份与恢复

建议标题：`feat(runtime): 新增经校验的阶段恢复与离线备份恢复`。依赖 PR1、PR2。

- [ ] 保存阶段依赖、输入/参数/版本指纹、产物清单；恢复先做只读预检。
- [ ] 支持路线阶段 SfM、MVS、3DGS 准备/训练、Fast3R；MVS 至少支持 dense/mesh/textured 边界恢复。
- [ ] SfM 内部特征/匹配/mapper 首版作为一个恢复单元，失败则重做 SfM；3DGS 训练与 Fast3R 推理从阶段起点重跑。
- [ ] 仅复用内容和来源校验通过的产物；前置阶段损坏时使依赖阶段失效；禁止仅凭 exists 或 completed 跳过。
- [ ] 每次恢复建立新 attempt 和独立工作目录，保留旧日志/产物及 task_id；失败尝试不可覆盖最后成功发布结果。
- [ ] 重复 resume 不产生两次活动尝试；新尝试通过相同队列和资源规则运行。
- [ ] 更新顶层摘要和模型登记，网页、评估与历史记录能够识别新结果且不混用旧 attempt 状态。
- [ ] 离线备份在同一工作区锁内冻结写入，SQLite backup API 导出库并做完整性/外键检查。
- [ ] 包含数据库、上传/登记照片、质量记录、输入快照、所有恢复依赖、模型、日志和任务配置；缺资产明确失败。
- [ ] 归档带格式版本、相对路径、大小、SHA-256 和工具版本；临时生成后验证并发布，排除工具、环境和锁文件。
- [ ] 恢复校验路径、链接、展开大小、哈希、数据库版本及关联，在新目录恢复，失败不发布半成品。
- [ ] 重写已知工作区绝对资产路径；原始 command 保留审计但不直接执行；旧 PID/设备分配不沿用，恢复后先停调度供核查。
- [ ] 更新三个核心文档、测试矩阵、公共使用指南和完整故障/备份恢复报告。

测试与验收：

- [ ] SfM 成功、MVS 失败后只重跑 MVS；dense 完成、mesh 失败后恢复 mesh/textured，不重算 dense。
- [ ] 删除/截断/篡改前置产物、修改输入或关键参数，预检识别并重算或明确拒绝复用。
- [ ] 恢复时资源不足排队；取消新尝试不改变旧尝试；旧监控更新不能覆盖新尝试状态。
- [ ] 在摘要发布前后、模型登记前后注入故障，重启后可收敛，不伪造成功或丢失历史。
- [ ] 临时工作区完整备份到另一根目录恢复，任务 ID、关系、文件哈希和历史预览一致。
- [ ] 篡改、截断、路径穿越、符号/硬链接、重复归档路径、磁盘不足及不支持版本均拒绝，原工作区不变。
- [ ] 至少一次真实 SfM/MVS 阶段恢复及离线备份演示；3DGS/Fast3R 按可用环境独立记录。

## 每个 PR 的合并门槛

1. 同一个 PR 包含代码、测试、文档；三个核心文档注明该 PR 哪些契约已实现、哪些仍计划中。
2. 执行专属测试和 `python -m unittest -v`；记录命令、数量、失败/跳过原因及环境。
3. 通过 [testing.md](testing.md) 中本 PR 的编号场景，保存可复现的演示步骤和实际结果。
4. 必要公共模块改动提前协调；权限模块由另一位组员实现，本模块提供项目归属和权限接入点。
5. PR 描述使用 `Refs #<总 issue 编号>`；PR1/PR2 不关闭总 issue，PR3 全部验收完成才使用 `Closes`。
6. 不提交数据库、照片、模型、备份包或凭据；不删除/弱化旧测试以通过检查。
